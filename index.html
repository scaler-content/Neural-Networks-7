What can a network learn without labels?

The closing question of the Neural Networks module.

Every model trained so far looked at an input and was told the right answer: this image is a cat, this house costs this much. Every one of those models depended on labels, and labels are expensive. Someone has to tag every image, every transaction, every review.

This read asks a different question: what can a network learn when nobody gives it the answer? By the end you will have trained a network that is never told what a digit is, and yet places the same digits close together. You will also see where the idea breaks, how to catch it when it does, and where it quietly runs inside AI systems in 2026.

01

Can a network copy its input?

From copying to compressing.

Take a network where every layer has the same number of neurons: six in, six, six, and six out. The input is xi and the output is x̂i. We want the output to equal the input. Is that possible?

Yes, and it is almost embarrassingly easy. Make every activation linear, set the weights to an identity matrix, and whatever goes in comes out. Gradient descent can even find this on its own. But notice what the network learned by doing this: nothing. It copied, and a network that copies gives no insight about the data.

So make the task harder in one specific way: squeeze the middle. Explore the three layouts below.

Adding a bottleneck

With the layout 6 → 4 → 2 → 4 → 6, can the output still equal the input? Approximately, not perfectly. We cannot hope for a perfect copy, so we choose a loss that measures how far off the reconstruction is. A common choice is the mean squared error:

L = 1n ∑i=1n ‖ xi − x̂i ‖²

Now the key idea. The middle layer has only two numbers. From those two numbers alone, the second half of the network has to rebuild all six original values. If it manages that well, those two numbers must have captured what matters about the input.

Encoder

The first half. It compresses the input down to the narrow middle.

Bottleneck

The narrow middle layer. Also called the latent representation, the code, or the embedding. All four names mean the same thing.

Decoder

The second half. It decompresses the code back into a reconstruction of the input.

The whole network is an autoencoder.

Key idea: self-supervised

There is no label anywhere in this setup. The input is its own target. That is why autoencoders are described as unsupervised, or more precisely self-supervised: the supervision signal is manufactured from the data itself.

If we only care about the code, why train a decoder at all?

Without the decoder there is no training signal. The decoder's job is to force the code to carry enough information to rebuild the input. We train the pair together and then keep the half we need, usually the encoder.

Why it is useful

Imagine a sparse 300-dimensional vector pushed down to 32 numbers. If the decoder can rebuild the 300 values from those 32, we have a compact description of the original: the data is compressed by reducing the number of features, and a shorter vector means faster models and lower latency downstream.

02

Undercomplete vs. overcomplete, and PCA

The width of the code decides what the network is forced to do.

Undercomplete

The code is narrower than the input. The narrow code does the work of forcing compression. Everything drawn so far is undercomplete.

Overcomplete

The code is wider than the input. Nothing forces compression anymore. This will cause trouble later in this read, and we will deliberately walk into it (section 07).

Is an autoencoder like PCA?

Yes. If the encoder and decoder are both linear and the loss is mean squared error, an autoencoder learns the same subspace as PCA, the one spanned by the top principal components. Add nonlinear activations and the autoencoder can capture curved structure that a straight-line projection cannot. In that sense, an autoencoder is a nonlinear generalization of PCA.

Does the decoder have to mirror the encoder layer by layer?

No. Mirroring is a convention that many tutorials follow. What matters is the bottleneck. Decoders are often shallower or deeper than the encoder depending on the task.

Interview angle: PCA is fast and needs no tuning. Why would anyone train an autoencoder instead?

Good reasoning: when the structure in the data is nonlinear, when the encoder must be reused on new data as a learned function, or when the data is too large for a full matrix decomposition.

A weak answer: “Because neural networks are more powerful than PCA.”

A strong answer: “I would fit PCA first as a baseline because it is cheap and interpretable. I would move to an autoencoder if the reconstruction error or the downstream metric shows that a linear projection is losing structure that matters, and I would accept the extra tuning cost only if it pays off.”

A habit worth keeping

Baseline first: try the simple thing, then justify the complicated one. The rest of this read follows that habit.

03

Building an autoencoder in PyTorch

Define it, train it, and see what “approximately equal” looks like.

The model is a stack of linear layers with ReLU between them, no activation after the last encoder layer (so the code is unconstrained), and a final sigmoid on the decoder that keeps each reconstructed pixel between 0 and 1, matching the input range. The decoder is the encoder's layer sizes in reverse.

Compression

The 32-unit code compresses each image by a factor of about 24.5 (784 ÷ 32).

Code: the model and the training helpers
def mlp(dims, last_act=None):
    """Linear layers with ReLU between them. No activation after the last layer unless last_act is given."""
    layers = []
    for i in range(len(dims) - 1):
        layers.append(nn.Linear(dims[i], dims[i + 1]))
        if i < len(dims) - 2:
            layers.append(nn.ReLU())
    if last_act is not None:
        layers.append(last_act)
    return nn.Sequential(*layers)


class AutoEncoder(nn.Module):
    def __init__(self, dims, out_act=None, code_act=False):
        super().__init__()
        enc_layers = list(mlp(dims))
        if code_act:                                   # optional ReLU on the code itself
            enc_layers.append(nn.ReLU())
        self.encoder = nn.Sequential(*enc_layers)      # input -> ... -> code
        self.decoder = mlp(dims[::-1], last_act=out_act)  # code -> ... -> reconstruction

    def forward(self, x):
        return self.decoder(self.encoder(x))


ae = AutoEncoder([784, 128, 64, 32], out_act=nn.Sigmoid()).to(device)
print(ae)
print("Parameters:", f"{sum(p.numel() for p in ae.parameters()):,}")


def add_noise(x, std):
    if std == 0:
        return x
    return (x + std * torch.randn_like(x)).clamp(0, 1)


def train_ae(model, x_tr, x_va, epochs=10, lr=1e-3, batch_size=256,
             noise_std=0.0, loss_fn=None, log_every=1):
    loss_fn = loss_fn or nn.MSELoss()
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    hist = {"train": [], "val": []}
    for epoch in range(1, epochs + 1):
        model.train()
        perm = torch.randperm(len(x_tr), device=x_tr.device)
        running = 0.0
        for i in range(0, len(x_tr), batch_size):
            xb = x_tr[perm[i:i + batch_size]]
            loss = loss_fn(model(add_noise(xb, noise_std)), xb)   # target is the CLEAN input
            opt.zero_grad()
            loss.backward()
            opt.step()
            running += loss.item() * len(xb)
        model.eval()
        with torch.no_grad():
            val = loss_fn(model(add_noise(x_va, noise_std)), x_va).item()
        hist["train"].append(running / len(x_tr))
        hist["val"].append(val)
        if log_every and epoch % log_every == 0:
            print(f"Epoch {epoch:3d}/{epochs}  loss: {hist['train'][-1]:.5f}  val_loss: {val:.5f}")
    return hist

What “approximately equal” means

Compared with the originals, the reconstructions are recognizable but softer. The worst ones are ambiguous or unusually written digits, which look blurrier or shifted. The reason is that mean squared error rewards predicting an average of plausible pixel values when the code cannot pin down the exact stroke. In short: 784 numbers were squeezed into 32 and rebuilt into something recognizable, but a 32-number code cannot hold every detail.

Important

The reconstruction loss is a training signal. It is not a report card for how good the code is. The next sections show exactly why.

Choosing the bottleneck size

The main design decision in an undercomplete autoencoder.

Change only one number, the code size, and watch validation reconstruction error. Four autoencoders (784 → 256 → k, with k = 2, 8, 32, 128) were each trained for 5 epochs.

Interview angle: how would you choose the bottleneck size in a real project?

Good reasoning: start from the constraint (storage, latency, or the input size the downstream model accepts), look for the elbow in the reconstruction curve, and confirm with the metric of the downstream task rather than reconstruction error alone.

A weak answer: “Pick the size with the lowest reconstruction error.”

A strong answer: “Reconstruction error always improves as the code grows, so it cannot choose the size on its own. I would set a budget from latency or storage, find the point where extra units stop paying off, and then validate on the task the code will be used for.”

05

What can two numbers say about a digit?

The worst reconstruction of all has one superpower: you can plot it.

The 2-unit code had the worst reconstruction error, so it is tempting to write it off. But there is one thing you can do with two numbers that you cannot do with thirty-two: plot them.

The experiment: compress every 784-pixel image into two numbers, use them as an x and y coordinate, and plot the test images as points. The loss only asks the network to redraw pixels, and digit identity appears nowhere in training. Afterward, each point is colored by its true digit, with the labels used only for coloring. What would you expect: a shapeless cloud, visible groups with some overlap, or ten cleanly separated clusters?

The result is visible groups with some overlap. The network was only ever asked to redraw pixels, and yet images of the same digit land near each other: ones are grouped, zeros are grouped, and the network was never told that a one exists.

Important: not a guarantee

The groups are not perfect. Fours and nines overlap, and so do threes and fives, because those digits look alike in pixel space. The autoencoder organizes images by visual similarity, which is close to class identity but not the same thing. That is why the code is treated as a feature to test, not a guarantee.

Three ways to get two coordinates

The lecture compares the 2-unit autoencoder against two baselines on the same 1,000 test images: PCA and t-SNE.

t-SNE looks cleanest. Why not just use t-SNE?

t-SNE has no encoder. It produces coordinates for the exact points it was given, and to place a brand-new image it has to be rerun. It also distorts distances, so it is only used for visualization. An autoencoder gives a reusable function that maps any new image to a code, which is what makes it usable in a product.

If an autoencoder generalizes PCA, why does PCA look worse here?

PCA is limited to straight-line projections, and two straight directions cannot unfold how handwritten digits vary. The nonlinear encoder can bend the space, which is the extra power the nonlinearity buys.

06

The encoder as a feature extractor

Mountains of unlabeled data, a handful of labels.

Structure is only valuable if it helps a task. The most common situation in companies is lots of unlabeled data and few labels, because labeling costs money. So: the 32-unit autoencoder was trained on all 60,000 training images without labels. Now suppose only 500 have labels. Train a simple classifier two ways, on the raw 784 pixels and on the 32-number code. Which scores higher on the test set?

Freezing the encoder in PyTorch

In a real pipeline you attach a small head to the encoder and decide which parts get trained. Freezing means setting requires_grad to False so the optimizer leaves those weights alone. The recipe has two modes:

Freeze when…

labeled data is tiny, or the new task is close to the pretraining data.

Fine-tune when…

there are enough labels and the new data differs from what the encoder saw, using a small learning rate. A common middle path: train the head first, then unfreeze the encoder gradually.

It is the same idea as taking a model trained on one medical imaging task and reusing it for another: keep the early layers that learned general structure, and retrain the part specific to the new task.

Important

Today's large pretrained encoders for images and text are usually trained with objectives such as contrastive learning or masked prediction, not pure reconstruction. The workflow is identical, though: pretrain on plentiful unlabeled data, then reuse the encoder.

Code: logistic regression on pixels vs codes, then a frozen encoder
from sklearn.linear_model import LogisticRegression

n_labeled = 500
torch.manual_seed(0)
idx = torch.randperm(len(x_train))[:n_labeled]
y_lab = y_train[idx].numpy()

ae.eval()
with torch.no_grad():
    x_lab = x_train[idx.to(device)]
    z_lab = ae.encoder(x_lab).cpu().numpy()
    z_test = ae.encoder(x_test).cpu().numpy()

raw_clf = LogisticRegression(max_iter=5000).fit(x_lab.cpu().numpy(), y_lab)
emb_clf = LogisticRegression(max_iter=5000).fit(z_lab, y_lab)

print(f"raw pixels    ({784:3d} features): {raw_clf.score(x_test.cpu().numpy(), y_test.numpy()):.3f}")
print(f"AE embeddings ({z_lab.shape[1]:3d} features): {emb_clf.score(z_test, y_test.numpy()):.3f}")

clf = nn.Sequential(ae.encoder, nn.Linear(32, 10)).to(device)   # note: ae.encoder is shared, so freezing it also freezes ae's encoder
for p in clf[0].parameters():
    p.requires_grad = False                                     # freeze the pretrained encoder

n_total = sum(p.numel() for p in clf.parameters())
n_train = sum(p.numel() for p in clf.parameters() if p.requires_grad)
print(f"trainable parameters: {n_train:,} of {n_total:,}")

opt = torch.optim.Adam(clf[1].parameters(), lr=1e-2)             # optimizer only sees the new head
xl, yl = x_lab, y_train[idx].to(device)
for step in range(300):
    loss = F.cross_entropy(clf(xl), yl)
    opt.zero_grad()
    loss.backward()
    opt.step()

with torch.no_grad():
    acc = (clf(x_test).argmax(dim=1).cpu() == y_test).float().mean().item()
print(f"frozen encoder + linear head, test accuracy: {acc:.3f}")

07

The identity trap and denoising autoencoders

Everything so far worked because the bottleneck squeezes.

A practitioner's instinct is often the opposite: a bigger network must learn better features. Nothing stops us from trying. Build an overcomplete autoencoder: 784 pixels into a code of 1,024 units, wider than the input, and back out to 784. The wider code has more capacity, so will reconstruction error on clean test images be higher, lower, or about the same as the 32-unit model?

Now give both models something they have never seen: digits with heavy random noise added. The 1,024-unit output keeps much of the grain and speckle of the noisy input, while the 32-unit output is smoother, because a 32-number code cannot carry the noise. (The wide model is not always a perfect copy, so keep the conclusion tied to the comparison: the wide model preserves noise that the narrow model cannot.)

The wide autoencoder found the shortcut from the start of this read: with a code wider than the input, it can pass pixels through and get a near-perfect score without learning anything about digits. This is the identity trap. The low loss was real, and it was also meaningless. The narrow model produced a cleaner picture almost by accident.

The fix: take the shortcut away

If copying is the shortcut, corrupt the input but keep the target clean. Copying the input now means copying the noise, which increases the loss. The only way to reduce the loss is to learn what digits actually look like and separate signal from noise. This is a denoising autoencoder. The architecture does not change; one argument does: noise_std=0.5.

Implementation detail worth checking

The noise is generated fresh for every batch in the training helper, so the network never sees the same corruption twice and cannot memorize one. Check this in any denoising implementation.

Bigger than MNIST

Corrupt-and-reconstruct is how denoising is done on sensor data and medical scans. It is also the core objective behind diffusion image generators, which are trained to remove noise, and behind masked pretraining, where a model reconstructs hidden parts of its input.

Interview angle: your autoencoder reaches near-zero training and validation loss. Do you ship it?

Good reasoning: no, not on that evidence. Check the code width against the input width, test on corrupted or out-of-distribution inputs, and evaluate the code on the downstream task.

A weak answer: “Yes, low validation loss means it generalizes.”

A strong answer: “Low reconstruction error only proves the model can reproduce its input. I would check whether the code is narrower than the input, feed it corrupted inputs to see whether it just copies them, and measure the downstream task before trusting it.”

AI-assisted debugging: diagnose a broken autoencoder

Use an assistant for hypotheses, then verify with numbers.

We spotted the identity trap because we knew to look for it. In practice a broken model arrives with no warning label. AI assistants can be a fast second pair of eyes, as long as you stay in charge of the reasoning: the AI's diagnosis is accepted only after the fix is run and the numbers change.

A teammate trained the same 32-unit architecture on MNIST and sent this result. Something is wrong.

7218.1training loss, epoch 1 (7217.3 at epoch 2)
7343.5validation loss, epochs 1 and 2: it does not drop meaningfully
No digitevery reconstruction looks nearly the same, with no digit in it

The workflow

  1. Run the cell and look at the loss values and the reconstructions.
  2. Before opening any AI tool, write down one sentence: your own hypothesis about what is wrong.
  3. Give an assistant the prompt below plus the printed model architecture (print(buggy)).
  4. Compare its ranked list with your hypothesis, and pick one proposed experiment you could run in under a minute.
  5. Run the fix and compare the numbers.
Prompt to use 
I trained an autoencoder on MNIST with layers 784 -> 128 -> 64 -> 32 -> 64 -> 128 -> 784, ReLU between layers, a sigmoid on the output, MSE loss, and Adam with learning rate 0.001. The training loss is in the thousands and does not drop meaningfully across epochs, and every reconstruction looks nearly the same, with no digit in it. Give me your top 3 hypotheses ranked by likelihood, and for each one a quick experiment that would confirm or rule it out. Do not rewrite my code yet.
The diagnosis

The input pixels range from 0 to 255 while the sigmoid output can only produce values between 0 and 1. The one-minute experiment is to print the minimum and maximum of the input. Some assistants will also suggest learning-rate or architecture changes; use the loss magnitude to discriminate between hypotheses. A loss in the thousands on data that should give a loss well below 1 points at a scale mismatch before it points at anything else.

After the fix (the only change: pixels scaled to [0, 1]) the loss drops from the thousands to a small fraction of one, and the reconstructions look like digits again. The lesson is about how to use the assistant: it proposed causes, and we tested them with numbers we could compute. A quick check of the input range would have caught this in seconds, and it is the first thing worth checking whenever a loss looks the wrong size.

09

Recommendations from sparse data

When most of the table is empty, missing is not zero.

So far the data was dense: every pixel had a value. Real business data is often the opposite. Picture a table where each row is a movie, each column a user, and each cell the rating that user gave. Most users have rated a tiny fraction of the movies, so most cells are empty.

The plan: treat each movie's row of ratings as the input, learn a dense embedding for it, and use the embeddings to find similar movies.

Many movies have only a handful of ratings, and a row with two ratings gives the network almost nothing to learn from, which is why teams set a minimum support.

Missing is not zero

To build the table, the empty cells were filled with zero. But a zero does not mean the user hated the movie; it means the user never rated it. With ordinary mean squared error over the whole row, most targets are zeros, and the easiest way to lower the loss is to predict zero almost everywhere. The fix: compute the loss only over entries a user actually rated, using a mask built from the target.

Important

This validation loss only says the model is not memorizing its training movies. It does not measure recommendation quality, because the held-out movies still show their ratings to the encoder.

Extract the embeddings, one 128-number vector per movie, and use cosine similarity to find the closest movies to a given one. Anomaly detection and the 2026 landscape

One more property of autoencoders, and where the ideas live today.

Reconstruction error as an anomaly detector

An autoencoder is only good at rebuilding the kind of data it was trained on. So rank every test image by its reconstruction error and look at both ends. The images rebuilt worst are the ones least like the rest of the data: unusual handwriting, very thick or very thin strokes, odd shapes. The claim to hold on to: high error means unusual compared with the training data, which is not the same as wrong.

In production, this is the idea behind anomaly detection: train an autoencoder on normal data (normal transactions, healthy machine sensor readings), choose a threshold from the errors on held-out normal data, and flag anything above it.

Interview angle: a fraud model flags a transaction whose reconstruction error is ten times the typical error. What can you conclude, and what can't you?

The transaction is unusual relative to the training data, which is not proof of fraud: it could be new but legitimate behavior. The threshold trades false alarms against missed cases, so flagged items go to review, and the data drifts, so the model needs monitoring and retraining.

The identity trap matters here too

An overcomplete autoencoder that copies its input reconstructs anomalies just as well as normal data, so nothing gets flagged. The bottleneck is what makes this technique work.

Autoencoders in the 2026 landscape

The movie pipeline you just built is the same shape as a great deal of modern AI. Select a stage to see its role.

Variational autoencoder

Adds one requirement: the code must follow a known distribution, so you can sample a new code and decode it into a new image. That step turns a compressor into a generator.

Latent diffusion

Image generators first compress images with an autoencoder, so the expensive diffusion process runs on small latent codes instead of raw pixels. The autoencoder built here is a small cousin of that first stage.

Important

Autoencoders are rarely the final answer in 2026. They are a building block. The reason to know them well is that their ideas (the bottleneck, the reusable encoder, and the corrupt-and-reconstruct objective) appear inside models much larger than this one.

Key takeaways

What to carry forward.

  1. An autoencoder is an encoder, a bottleneck and a decoder, trained to reconstruct its own input, with no labels anywhere.
  2. The bottleneck is the constraint. Without it, an autoencoder learns to copy, and the loss looks excellent while nothing is learned. A denoising objective removes the shortcut even when the code is wide.
  3. The code is reusable: a feature set for small labeled datasets, a coordinate system for visualization, and an embedding for similarity search. Freeze the encoder when labels are scarce and fine-tune when they are plentiful.
  4. Low reconstruction error is not the same as a good representation, so always test the code on the task it will serve. Match the objective to the data, as in masking the loss for missing ratings.
  5. Use AI to generate hypotheses, then verify them with experiments you can run.
